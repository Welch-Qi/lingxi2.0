## 一、背景

`lingxi-customer` 模块目前**只有 4 个 `package-info.java`（空骨架）**，
全仓 **0 个 Controller / 0 个 Mapper**。隔离套件 ①②⑤ 依赖的
`/api/v1/cus/customers*` 端点**全部不存在**。

这是「客户中心」这条业务主线从 0 到 1 的**第一个可交付切片**：
只做客户档案的读写，验证四道防线（租户拦截器 → 数据权限 → RLS → 隔离用例）在真实业务代码里闭环。

## 二、任务范围（IN SCOPE）

### 2.1 分层产物（严格按 `app → domain ← infra`，规约 §4.1）

```
com.lingxi.cus.api      ← 契约 DTO + 接口定义（禁放实现）
com.lingxi.cus.domain   ← 领域模型 + 仓储接口（禁出现 Spring/MyBatis/HTTP 类型）
com.lingxi.cus.infra    ← MyBatis-Plus Mapper + DO/PO 转换 + 仓储实现
com.lingxi.cus.app      ← Application Service（编排：权限校验 → 事务 → 仓储 → DTO 转换）
```

> **ArchUnit 会在 CI 强制校验分层**（`yuanshu-platform` 的 `ArchitectureRuleTest`），
> 写完本地必须跑通该测试。

### 2.2 端点（以 M0201-001 契约为准，此处为契约期望的形态）

| 端点 | 说明 | 对应隔离项 |
|---|---|---|
| `GET /api/v1/cus/customers/{id}` | 客户详情；越权访问须 403/404 | ① |
| `GET /api/v1/cus/customers?pageNo&pageSize` | 客户列表；**响应含 `tenantId`** | ② |
| `GET /api/v1/cus/customers/export?format=csv` | CSV 导出 | ⑤ |
| `POST /api/v1/cus/customers` | 新建客户（写操作，须幂等键） | — |
| `PUT /api/v1/cus/customers/{id}` | 更新客户 | — |
| `DELETE /api/v1/cus/customers/{id}` | 逻辑删除（`is_deleted=1`） | — |

### 2.3 必须落地的四道防线（**本任务的核心验收点**）

| 防线 | 实现位置 | 要求 |
|---|---|---|
| ① 租户拦截器 | `yuanshu-starter-mybatis` 的 `TenantLineInnerInterceptor` | **自动**，业务代码不写 `tenant_id` 条件；Mapper 查询无需手写租户条件 |
| ② 行级数据权限 | `owner_user_id` / `region_code` / `market_code` 三个维度（02-data 03 篇 §1.1） | 用 `@RequireDataScope` + `DataScope` 注解；scope 取自 Casbin 策略（SELF/DEPT/DEPT_AND_SUB/ALL） |
| ③ PostgreSQL RLS | `YuanshuRlsSessionInterceptor`（已就位） | **自动**；应用连接必须能读到本租户数据 |
| ④ 隔离测试用例 | `verify-tenant-isolation.sh` | ①~⑤ 可执行 |

> **③ 已在 2026-10-23 打通**（`YuanshuRlsSessionInterceptor` 写 `app.tenant_id` 会话变量）。
> 若查询返回 0 行，先确认 `TenantContext` 已被 `TenantContextFilter` 注入
> （Filter 在 `yuanshu-starter-security`，从 JWT 的 `tenant_id` claim 取租户，
> 并与 `X-Tenant-Id` 头**一致性比对**，不一致即 403）。

### 2.4 其他强制要求

- **ID 一律雪花 `Long`**（`id-type: assign_id`，DB 已配），禁 UUID / 禁自增
- **金额用 `Long`（分）**；时间用 `Instant` / `OffsetDateTime`（UTC）
- **分页响应固定** `{ list, total, pageNo, pageSize }`，`pageSize` 默认 20、上限 200
- **统一响应体** `R<T>`（`com.yuanshu.starter.core.web.R`）
- **写操作幂等**：消费 `X-Idempotency-Key`，按 `key + tenantId` 去重
- **禁止**：拼接 SQL、`System.out`、`printStackTrace()`、`new Thread()`、`Executors.newXxx()`、
  `@Value` 散落取值、`System.getenv`、浮点金额、空 catch、无 where 的 update/delete
- **方法 ≤80 行 / 类 ≤600 行**
- **`stage` 列不得读**（V2.1.1 已停用），列表筛选按「客户类型 + 价值分层」

## 五、待决策（须人工裁决）

1. **导出 CSV 的规模上限**：一次导出最多多少行？超出是截断还是拒绝？
   建议：上限 10 万行，超出报 `A0xxx` 提示用筛选条件缩小范围。
2. **`cus_customer.entity_id` 的写入时机**：客户建档时 `entity_id` 必填（NOT NULL），
   指向 `dt_entity_company.id`；但企业实体消歧（M1200-002）尚未实现，
   客户建档时如何拿到 `entity_id`？
   建议：**先做「从既有 `dt_entity_company` 选」**，不自动调消歧接口
   （消歧 API 就绪后再接）。
3. **`customer_type`（E59）的初值**：建档时取哪个值？
   建议：默认 `NEW_POTENTIAL`（新潜客户），后续由商机成交关闭事件驱动变更。
4. **`tier`（E28）初值**：建议默认 `C`（小微客户），季度复核时调整。
