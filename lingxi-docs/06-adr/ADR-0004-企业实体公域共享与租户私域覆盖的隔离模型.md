## 修订记录（V2 · 2026-10-14）

V1 决策「企业实体采公域共享 + 私域覆盖」，其前提是「`dt_*` 实体表当前在白名单、无 `tenant_id`、RLS 未开」。**逐表核对已落地的 Flyway 基线后该前提不成立**：

| V1 的前提 | 代码实况（`V202609111040__dt_init_baseline.sql`） | 判定 |
|---|---|---|
| `dt_entity_company` 公域共享、**无 `tenant_id`** | DDL 第 3 列即 `tenant_id BIGINT NOT NULL` | ❌ 不符 |
| `dt_entity_company` **RLS未开** | 已有 `ALTER TABLE dt_entity_company ENABLE ROW LEVEL SECURITY` + `CREATE POLICY p_dt_entity_company_tenant` | ❌ 不符 |
| `dt_entity_source_map` 在白名单、**需转私域** | 已有 `tenant_id` 与 `p_dt_entity_source_map_tenant` 策略 | ❌ 已是私域且已有 RLS |
| 白名单是「10 张业务资产表」 | `application.yml` `yuanshu.tenant.white-tables` 实际仅 **7 项系统表**，**不含任何 `dt_*`** | ❌ 不符 |

**V2 核心修订**：核心问题「`dt_entity_company` 取公域共享还是租户私域」经裁决取 **A1 · 顺代码 = 租户私域**。即：代码现状（实体主档按租户分档、租户级RLS）就是最终口径，不改代码。V1 中「公域共享 + `cus_entity_overlay` 私域覆盖」的表述相应调整为「实体主档按租户分档，跨租户消歧由元枢统一映射」。

## 背景

灵犀是多租户 SaaS。L1 数据底座的**企业实体中心**（`dt_entity_company` / `dt_entity_contact` / `dt_entity_source_map` / `dt_entity_review_queue`）承载企业实体档案，天然指向真实世界中存在的企业法人；同一德国采购商可能被多个租户分别引用。与之相对：

- **触达账号资产** `dt_account_asset`（发送类：邮件 / WhatsApp / 社媒）与 **社媒账号业务档案** `mkg_social_account` 属租户自己的运营资产；
- **退订名单** `mkg_unsubscribe`（合规必需）作用域存疑：是「同一邮箱跨全平台退订」还是「仅在本租户退订」；
- **工单** `svc_*`（OP-SVC）跨租户/坐席池共享亦属同类问题。

02-data Wave 0 ⑤ 曾把「实体白名单 + 无 `tenant_id`」列入临时状态；但落地 Flyway 基线时，实体主档按**租户分档**实现（`tenant_id` + RLS），与02-data 的「公域白名单」口径互斥。该互斥不裁决就会在「跨租户能否共享一家企业主档」上反复漂移，故立本 ADR。

## 决策

**采「方案 A1：实体主档按租户分档（顺代码），跨租户消歧由元枢统一映射；触达资产与退订一律留在租户私域」。**

- **实体主档 = 租户私域（RLS on，`tenant_id` 前缀唯一索引）**，与代码现状一致，**无需改动已执行的 Flyway 基线**：
  - `dt_entity_company`（企业主档，`uk_dt_entity_domain (tenant_id, lower(domain))` 租户内唯一）
  - `dt_entity_contact`（企业级「人」权威；Wave 0 ① 已定 L1 存人 / L2 存客户内角色，`cus_contact` 可空引用 `dt_entity_contact.id`；**该表尚未建，随后续 Wave 落地，须同样带 `tenant_id` + RLS**）
  - `dt_entity_relation`（实体关系；已有 `tenant_id`）
  - `dt_entity_source_map`、`dt_entity_review_queue`：**均为租户私域**（代码已具备 `tenant_id`；`source_map` 已有 RLS，`review_queue` 待补 RLS）
- **跨租户消歧（公域语义的新载体）**：不再靠「一张公域实体表」，改为由**元枢侧维护实体映射关系**（同一实体的跨租户对应），集群通过元枢 `api` 包消费。映射表归属与字段级建模归元枢语义本体，另开ADR/Wave，本 ADR 只定「不落在灵犀侧业务库」这一边界。
- **触达账号与退订（维持 V1 结论，代码尚未落地，须后续 Wave）**：`dt_account_asset`、`mkg_social_account`、`mkg_unsubscribe` **均为租户私域**，`UNIQUE(tenant_id, 业务键) WHERE is_deleted=0`，RLS 兜底。
- **工单 `svc_*`（OP-SVC）**：一期**按租户私域建模**（承本 ADR 精神），跨租户共享坐席池不在本期范围；如后续需要，再开新 ADR。

## 理由

1. **顺代码、不推翻已落地的安全默认值**：实体主档已带 `tenant_id` 且已开 RLS（`p_dt_entity_company_tenant` / `p_dt_entity_source_map_tenant`）。改为公域需补新 Wave 迁移、删 RLS、重设计唯一索引，且必须推翻「实体按租户隔离」这一更安全的默认 —— 收益（跨租户一企一条）不足以抵偿代价。
2. **「一企一档」语义由元枢承载，而非业务库表结构**：跨租户共指是**语义问题**，应由元枢的实体消歧/映射能力解决，不宜把「全平台唯一」的约束下沉到灵犀侧业务表。
3. **私域修改只落本租户档，不回写他人档**：租户对实体的归属人 / 标签 / 覆盖名等私域修改，只写自己租户的 `dt_entity_company` 行；**不得跨 `tenant_id` 触达其他租户的实体档**。
4. **触达账号与退订越权风险最高**：`credential_ref` 明文不出网关已是红线；跨租户可见 = 直接越权。退订作用域若采全局（方案 C）涉 GDPR / CAN-SPAM 数据滥用，须法务另批——因此**默认走A1、不退化到 C**；若法务后续判定某类退订（如平台级黑名单）必须全局生效，另立 ADR 补一小张全局表，不回退本决策。
5. **`dt_entity_source_map` / `review_queue` 本就是私域**：来源映射与人工消歧复核队列本质是「某租户如何解释这条外部数据」，属私域判断；代码已按此实现（`source_map` 连RLS 都已就位），只需给 `review_queue` 补齐 RLS 并补隔离测试。
6. **工单先租户私域**：一期不承诺跨租户坐席共享，避免与 `svc_*` 尚未展开的字段级建模耦合。

## 被否方案

| 方案 | 否决理由 |
|---|---|
| A2 · 实体主档改公域共享（V1 原始取向：一张表、无 `tenant_id`、RLS=off） | 需补新 Wave 迁移、删已开 RLS、重设计唯一索引，且推翻「实体按租户隔离」这一更安全的默认；跨租户共指是**语义问题**，应由元枢消歧能力承载，不宜下沉为业务表约束（详见修订记录） |
| B · 公域表的租户 fan-out 复制 | 一企多份权威，外部明细更新需 fan-out，统计口径易漂移；跨租户消歧仍无解 |
| C · 退订平台全局生效 | 把一个租户收到的退订扩散至全租户 = 数据滥用；GDPR/CAN-SPAM 合规风险；须法务先判，不能作为默认 |
| 触达账号做平台共享（连接器池化） | 凭证与租户业务边界绑定（发件人身份、渠道健康度、退订回流都是租户级），共享即越权 |

## 影响与后续约束

- 【强制】**已落地代码不动**：`dt_entity_company` / `dt_entity_source_map` 的 `tenant_id` + RLS 保持现状，**禁止**为「对齐公域口径」而删除或改写已执行的 Flyway 基线脚本。
- 【强制】**`dt_entity_review_queue` 补 RLS**：现状 DDL 有 `tenant_id` 但**未开 RLS**（`dt` 基线仅给 `entity_company` / `source_map` / `knowledge_embedding` 三表开策略），须补 `p_dt_entity_review_queue_tenant`，写法对齐既有策略：`USING (tenant_id = sys_current_tenant()) WITH CHECK (tenant_id = sys_current_tenant())`。
- 【强制】**其余 `tenant_id` 表的 RLS 缺口**（同批核查发现，一并补齐或明确排期）：`dt_entity_relation` / `dt_data_source` / `dt_metric_definition` / `dt_quality_issue` / `dt_quality_rule` / `dt_tag` / `dt_tag_relation` —— 均有 `tenant_id` 但未开 RLS。
- 【强制】**`dt_entity_contact` 随后续 Wave 建表**：须带 `tenant_id` + RLS，不得建成无 `tenant_id` 的公域表（该表当前迁移脚本中不存在）。
- 【强制】**`dt_account_asset` / `mkg_social_account` / `mkg_unsubscribe` 的 DDL**（当前迁移脚本中均不存在）：`UNIQUE(tenant_id, 业务键) WHERE is_deleted=0`；`mkg_unsubscribe` 采「本租户退订」口径，索引为 `UNIQUE(tenant_id, channel_type, target_norm)`；隔离测试用例必覆盖 `verify-tenant-isolation.sh`。
- 【强制】**白名单无需为实体表改动**：`application.yml` `yuanshu.tenant.white-tables` 实际仅 7 项系统表（`sys_dict_type` / `sys_dict_item` / `sys_i18n_message` / `sys_country` / `sys_currency` / `sys_metric_catalog` / `casbin_rule`），**不含任何 `dt_*`**。V1 中「白名单从 10 张业务资产表收缩」的整改事项**整条撤销**。
- 【推荐】`TenantTableWhiteList` 的 getter/setter 类型一致性核查仍建议做一次（历史陷阱：getter 返 `Set` / setter 接 `List` 会静默失效）—— 经核当前实现为 `Set<String> getWhiteTables()` + `setWhiteTables(List<String>)` 内部转 `HashSet`，**现状正确**，但新表加入白名单时须复核。
- 【强制】**跨租户实体消歧归元枢**：实体映射/消歧能力落在元枢语义本体，集群经其 `api` 包消费；映射表字段级建模另开 ADR/Wave，**不在灵犀侧业务库建跨租户共享表**。
- 【推荐】法务若后续判定某类退订（如平台级黑名单）需全局生效，另立 ADR-0005+ 补一小张 `sys_unsubscribe_global` 全局表，与本 ADR 并存，不回退本决策。
- 代价：跨租户识别「同一家企业」需经元枢映射层，不能直接跨租户 JOIN 业务表；比单表略复杂，通过应用层聚合可屏蔽，成本可控。
