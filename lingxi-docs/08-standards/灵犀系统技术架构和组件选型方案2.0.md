## 一、架构总则

### 1.1 八条架构铁律

| # | 铁律 | 含义 | 违反判定（可被机器检出） |
|---|---|---|---|
| 1 | 服务边界即组织边界 | 模块间只经 API 契约与领域事件通信，禁止跨边界直连数据库 | 出现跨模块表 JOIN |
| 2 | API-First | 任何对外能力先冻结 OpenAPI 3.0 契约再写实现 | 先写 Controller 后补文档 |
| 3 | 无状态水平扩展 | 应用层无状态，会话与任务状态外置 | 服务本地存 session 或文件 |
| 4 | 默认异步 | 跨模块业务流转用事件，同步调用只用于强一致性读 | 跨模块同步链路超过 3 跳 |
| 5 | 配置外置 | 环境差异、业务参数、模型地址、连接串全部走配置 | 代码中出现 IP / 密钥 / 模型名 |
| 6 | **双通道同源** | 人工操作与智能体执行走**同一套应用服务、同一张表**，禁止为智能体开影子 API | 存在绕过业务校验的 `/api/agent/**` 写接口 |
| 7 | **文档即权威** | `docs/` 五件套为唯一事实源；代码与文档冲突时默认代码错 | 无契约先行的接口 / 文档缺失的模块 |
| 8 | **环境即代码** | 环境启停、迁移、体检、发布全部脚本化且幂等；Agent 不得手工操作环境 | 存在非脚本化的环境操作记录 |

> 第 6 条是"人机融合 Native"的技术底线：**智能体只是另一种调用方，不是特权调用方**。第 7、8 条是 AI Coding 可商业化交付的前提。

### 1.2 三条边界约定

| 边界 | 约定 |
|---|---|
| **语言边界** | 业务逻辑只写 Java；前端只写 TypeScript；Python 仅用于数据采集与算法任务（独立进程，不承载业务规则）。禁止在 Java 里写 AI 编排（用框架），在 Python 里写业务规则 |
| **数据边界** | PostgreSQL 是唯一 OLTP 权威源；检索、向量、缓存、分析聚合都是**派生视图**，可重建，不作为事实来源 |
| **智能体边界** | 智能体访问业务只经**工具网关（MCP）**；禁止直连数据库、禁止绕过权限与租户隔离；越界请求拦截并转人工 |

### 1.3 五条选型标尺

| 标尺 | 判定标准 |
|---|---|
| 开源优先 | 只用 OSI 批准许可证：MIT / Apache-2.0 / BSD / MPL-2.0 / PostgreSQL License。**排除 SSPL、BSL、RSALv2、Elastic License、GPL-3.0 类** |
| 商业友好 | 允许闭源 SaaS 商业交付，无"网络服务 copyleft"义务，无按席位/营收收费条款 |
| 成熟稳定 | ≥3 年生产验证、近 6 个月有社区提交、有主流厂商落地案例；**版本只选已发布 ≥6 个月的稳定版** |
| 最小组件数 | 能用已有组件承载的能力不引入新中间件——每多一个组件 = 多一条 SSH 隧道 + 一个故障点 + 一个攻击面 |
| AI Coding 友好 | 强类型、约定优于配置、训练语料丰富、静态分析与测试工具链成熟 |

### 1.4 技术栈基线（一句话结论）

> **JDK 25 LTS + Spring Boot 4.1 模块化单体 + PostgreSQL 17（含 pgvector/pg_trgm/RLS） + Valkey 9 + Keycloak + Casbin + LangChain4j / Spring AI 2.0 + React 19 + Vite + Ant Design 5；全链路云主机进程化，无容器。**

### 2.2 架构形态与部署单元

| 部署单元 | 形态 | 说明 |
|---|---|---|
| **lingxi-server** | 模块化单体（一个 jar） | 11 个业务模块 + L0 公共服务；严格包边界；模块间走 Java Interface + 领域事件 |
| **lingxi-agent-runtime** | 独立进程 | 智能体编排、工具调用、任务状态持久化；独立伸缩，故障不影响业务主流程 |
| **lingxi-data-jobs** | 独立进程 | 外部数据源拉取、清洗、实体归并批处理 |
| **lingxi-web** | 静态站点（React SPA） | 单应用、路由分区，不做微前端；Nginx/CDN 托管 |
| （可选）**lingxi-data-worker** | 独立进程（Python） | 仅当需要爬虫、复杂特征工程、模型训练时启用；一期空缺 |

**架构形态结论**：**模块化单体 + 单一 SPA + 三个独立进程**。一期 98 项功能、团队规模小，微服务成本远大于收益；但**模块边界从第一天严格划定**（包结构 + ArchUnit 校验 + 只经 Interface 通信），二期任一模块可整体剥离为独立服务，业务代码零改动。

### 2.4 三条数据通道

```
① 人工通道
  React SPA → Nginx → Gateway → lingxi-server 模块
    → 认证过滤器（Keycloak JWT）→ 权限拦截器（Casbin 三层）→ 多租户拦截器（注入 tenant_id）
    → 应用 Service（业务规则 + 状态机）→ MyBatis-Plus → PostgreSQL
    → 领域事件（Outbox）→ Valkey Stream → 消费者（通知 / 数据沉淀 / 智能体触发）

② 智能体通道
  业务事件 / 定时触发 → lingxi-agent-runtime（任务队列）
    → 编排（LangChain4j agentic：路由 / 链式 / 并行 / 监督者）
    → 工具调用 → 工具网关（自主度校验 + 边界拦截 + 租户上下文注入）
    → 调用与人工通道**完全相同**的应用 Service → 同一张表
    → 产出落库 → 标记 source_type=AGENT → 界面提示可接管

③ 数据底座通道
  外部数据源（定时任务）→ 接入层（限速 / 重试 / 质量标记）
    → 企业实体中心（规范化 → 域名/名称强匹配自动归并 → 地址+行业弱匹配进人工队列）
    → 明细层 → 资产层（图谱 / 标签 / 指标）→ 应用层（画像 / 评分 / 预警数据服务）
    → 供经营分析智能体与业务界面调用
```

**核心结论**：人工与智能体**共用同一个 Application Service 与同一张表**，写入时统一标记 `source_type`（HUMAN / AGENT / SYSTEM），从数据层根除"影子数据"，这是"同源铁律"的工程落地。

### 2.5 部署架构（无容器）

```
                     ┌── Nginx（反向代理 + 静态资源 + HTTPS 终止）×2
云主机（应用组）      ├── lingxi-server（Spring Boot jar，多实例 + 进程守护）
                     ├── lingxi-agent-runtime（独立进程）
                     ├── lingxi-data-jobs（独立进程，单实例）
                     └── Nacos（注册与配置）

云数据库             PostgreSQL 17（主从 + 自动备份 + WAL 归档）
云缓存               Valkey / 兼容服务（主从 + 哨兵）
云存储               对象存储（S3 兼容 + CDN）
静态资源             前端构建产物（CDN 分发）
```

| 项 | 方案 |
|---|---|
| 进程管理 | systemd：`Restart=always` + 日志接 journald，每服务一个 unit |
| 发布 | 脚本化灰度：新版本目录 → 启动新实例 → 健康检查通过 → 切换 Nginx upstream → 停旧实例 |
| 数据库变更 | Flyway 版本化脚本；只增不改不删（前向兼容）；每次变更附回滚预案 |
| 回滚 | 保留上一版本产物，脚本一键切换（目标 < 5 分钟） |
| 配置 | Nacos（环境配置）+ 数据库（业务配置）；凭证走环境变量或密钥服务，**永不入库入代码** |
| 容器化 | **全链路不使用 Docker / K8s** |

**环境规划**：

| 环境 | 用途 | 数据与中间件 |
|---|---|---|
| dev | 开发联调 | DB + 缓存用**云端服务**，本地经 **SSH 隧道**连接（只连本地映射端口 `127.0.0.1:13306/16379`） |
| test | 测试 | 独立实例；每次部署自动跑全量测试 + 租户隔离套件 |
| staging | 预发布 | 生产同构、脱敏数据、**通道全部 Mock（绝不真发营销邮件）** |
| prod | 生产 | 云数据库（主从）+ 缓存（主从哨兵）+ 对象存储 + CDN |

## 四、关键架构设计结论

### 4.1 多租户与数据隔离

| 层面 | 结论 |
|---|---|
| 隔离模型 | 一期**共享库 + 共享表 + `tenant_id` 列**；二期起为大客户提供独立 Schema（迁移单元清晰） |
| 强制注入 | MyBatis-Plus 租户插件自动注入；**全局表白名单制**（仅字典/平台配置免注入），新增表默认必须带租户列 |
| 上下文传递 | JWT 携带 `user_id / tenant_id / roles` 摘要 → 服务端解析写入 ThreadLocal；**跨线程（虚拟线程/异步）必须显式传播** |
| 双重防线 | ① 应用层拦截器注入；② **PostgreSQL RLS 兜底**——即使应用层漏写 `where tenant_id` 也无法跨租户读 |
| 配额计量 | 租户级配额账本表：API 调用量、LLM Token、存储、账号数、发信量；执行点在网关与 LLM 调用处 |
| 智能体隔离 | 工具网关注入租户上下文；RAG 向量表同样带 `tenant_id` 过滤；**智能体不得跨租户检索** |

### 4.2 认证与权限

| 项 | 结论 |
|---|---|
| IdP | **Keycloak 26.x**：OIDC / OAuth2.1；**Realm 天然对应租户**；内置用户管理、社交登录、MFA、用户联邦 |
| 不自研 | 认证是最不该自研的模块（密码策略、Token 轮换、防爆破、合规），集成优于自研 |
| 客户端 | SPA 用 Authorization Code + PKCE；服务间用 Client Credentials；智能体用独立 client + 严格 scope |
| Token 策略 | Access Token 15 分钟 + Refresh Token 轮换 + 吊销黑名单（Valkey）；JWT 只放摘要，**完整权限实时走 Casbin 决策** |
| 登录方式 | 账号密码 + 图形验证码；预留企业微信/钉钉/飞书 SSO（Keycloak IdP 配置即可，不改业务代码） |

**权限三层叠加**：

| 层 | 模型 | 技术实现 | 产品对应 |
|---|---|---|---|
| 功能权限 | RBAC（角色-菜单-按钮），权限码 `{域}:{对象}:{动作}` | Casbin policy 表 | CC 功能权限 |
| 数据权限 | 行级：`SELF / DEPT / DEPT_AND_SUB / CUSTOM / ALL` | MyBatis-Plus 数据权限拦截器 + Casbin 数据策略；维度含归属人/部门/区域/市场 | CC 数据权限 |
| 字段权限 | 字段级可见 / 可编辑 | 序列化层动态脱敏（注解 + 拦截器）；成本价、利润率默认隐藏 | CC 字段权限 |

> 性能设计：Casbin enforcer 全量策略常驻内存 + Valkey 发布订阅做多实例失效通知；决策为本地内存计算（微秒级），无远程调用。

### 4.3 全球化架构

| 能力 | 结论 | 产品对应 |
|---|---|---|
| 界面多语言 | 前端 react-i18next + ICU；**后端返回消息码 + 参数而非文案** | CC 语言配置 |
| 内容多语言 | LLM 生成/翻译（116 语种）；多语言字段存 **JSONB**；跨域 API 必须显式带 `locale` | AI 写信、话术库 |
| 多币种 | 金额一律**最小货币单位整数**存储（禁浮点）；汇率快照随单据固化，历史单据金额永不变动 | CC 币种配置 |
| 多时区 | 数据库统一存 **UTC**；展示按用户时区、触达按客户时区；定时任务按目标时区投递 | CC 时区配置 |
| 区域格式 | 数字/日期/地址按 locale 适配（Intl API） | 全局交互规范 |
| 海外访问 | 静态资源 CDN 加速；海外就近接入；触达通道（邮件/WhatsApp）海外部署保送达率 | 高送达率保障 |
| 数据合规 | 租户数据分类分级标记；GDPR/PIPL 导出与删除接口预留（软删除 + 定期物理清理） | 安全策略 |

### 4.4 L1 数据底座

**技术形态结论**：L1 **不是新的存储系统**，而是 PostgreSQL 内的一组**规范化表 + 物化视图 + 定时任务**（与业务库不同 Schema，可同事务写入）。

**四层结构**：

| 层 | 内容 | 技术承载 |
|---|---|---|
| ① 接入层（DT-01） | 数据源注册 · 调度编排 · 增量同步 · 限速重试 · 健康监控 | `DataSourceAdapter` 适配器模式（源可插拔） |
| ② 明细层 | 企业实体（统一 ID）· 联系人 · 客户 · 商品 · 订单 · 跟进 · 内容 | 规范化表 |
| ③ 资产层（DT-04/05） | 企业图谱 · 产品图谱 · 标签体系 · 指标体系 | 关系表 + 递归 CTE + 标签关联表 + 指标定义表 |
| ④ 应用层 | 画像 · 评分 · 推荐 · 预警 · 报告的数据服务 | 视图 / 物化视图 / 数据服务 API |
| 贯穿 | 数据质量监控（DT-06）· 清洗去重（DT-03）· 即时沉淀（DT-07） | 规则任务 + Outbox 消费者 |

**企业实体中心（DT-02，壁垒枢纽）** —— 核心表与归并规则：

```sql
data_entity_company          -- 企业实体主表（一企一档，统一实体ID）
data_entity_source_map       -- 多源映射（CUSTOMS/GLOBAL_DB/SOCIAL/CRM/MANUAL）
data_entity_review_queue     -- 弱匹配人工确认队列
data_entity_relation         -- 关系边（CONTACT_OF/SAME_GROUP/SUPPLIER_OF/COMPETITOR_OF）
```

| 步骤 | 规则 | 处置 |
|---|---|---|
| ① 规范化 | 去法律后缀（Ltd/LLC/GmbH/Co.,Ltd…）、去标点空格、大小写归一、域名去协议去 www | — |
| ② 强匹配 | **域名完全一致** 或 **规范化名称完全一致** | 自动归并，写 `source_map` + `match_rule` |
| ③ 弱匹配 | 国家+城市一致 且 行业一致 且 名称相似度 **≥0.85** | 写入人工确认队列（界面：实体合并/拆分） |
| ④ 兜底 | 无匹配 | 建为新实体，保留来源标记，低置信度 |
| ⑤ 纠错回写 | 人工确认/拒绝结果 | 回写规则库，提升后续准确率 |

技术手段：`pg_trgm` 相似度 + GIN 索引；名称规范化用 PG 函数 + 可配置多语言后缀词典；归并**可逆**（`is_merged` + `merged_into_id`，不物理删除）。

**指标体系**（问答式取数的前提）：`metric_definition` 表定义 `metric_code / formula_type / sql_template / available_dimensions / available_filters / unit / owner / version`，全系统同一口径。

**即时沉淀（DT-07）**：业务 Service 写业务表**与**写 Outbox 记录在**同一事务** → 轮询（ShedLock 单实例）投递 Valkey Stream → 消费者（数据沉淀 / 通知 / 智能体触发 / 审计 / 质量检查）；事件带唯一 ID + 消费幂等表。

**问答式取数链路（DM-02）**：

```
自然语言问题
 → ① 意图识别（LLM）→ ② 槽位抽取（仅允许从指标元数据的 available_dimensions/filters 取值）
 → ③ 语义层映射为参数化 SQL 模板 → ④ 受限执行（强制注入 tenant_id + 数据权限 + 只读账号 + 超时/行数上限）
 → ⑤ 结果解释（LLM：数据 + 结论 + 图表建议，结构化输出）→ ⑥ 前端渲染（ECharts）
```

> **安全约束**：LLM **不直接生成 SQL**，只生成"指标 + 维度 + 筛选"结构化参数，SQL 由服务端模板拼装——从根本消除 SQL 注入与越权查询。

### 4.5 L3 智能体层与人机协同

**三层分工（各司其职，不混写）**：

| 层 | 载体 | 场景 | 典型能力 |
|---|---|---|---|
| ① 业务内嵌 AI | Spring AI 2.0（`lingxi-server` 进程内） | 单轮、低延迟、与业务强耦合 | 智能建档补全 · 字段补全 · 跟进记录草稿 · 邮件分类 · 话术推荐 · 单轮内容生成 · 取数语言理解 |
| ② Agent Runtime | LangChain4j（独立进程） | 多步骤、长时运行、需工具编排与人工介入 | 客户开发序列 · 市场扫描报告 · 内容批量生产 · 社媒排期运营 · 客服接待与工单 · 经营分析 |
| ③ 智能体中心 | `lingxi-agent`（管理面） | 配置与治理，不执行任务 | 智能体配置 · 调度 · 监控 · 效能评估 · 模型注册 · 技能目录 · MCP 服务器管理 · 审批看板 |

**六大智能体编排实现**：

| 智能体 | 编排模式 | 关键工具（MCP） | 自主度默认 |
|---|---|---|---|
| 客户开发（AG-01） | 监督者 + 链式（检索→筛选→触达序列→意向评分） | 企业实体检索 · 线索创建 · 邮件/WhatsApp 发送 · 意向评分 | 触达 A1（人审），名单 A2 |
| 市场分析（AG-02） | 并行（多维数据并行拉取）+ 汇总生成 | 搜索趋势查询 · 贸易数据查询 · 报告生成 | A3（仅内部） |
| 内容创意（AG-03） | 链式（选题→生成→品牌校验→多语言本地化） | 素材检索 · 品牌规范读取 · 内容草稿创建 | A1（对外内容必须人审） |
| 社媒运营（AG-04） | 定时 + 路由（发布/互动/监测分流） | 账号健康查询 · 排期发布 · 评论回复草稿 · 询盘转线索 | 发布 A1，监测 A3 |
| 营销客服（AG-05） | 路由（接待/答疑/跟进/售后分流）+ 中断（转人工） | 客户 360 查询 · QA 匹配 · 跟进记录创建 · 工单创建 | 接待 A2，对外回复 A1 |
| 经营分析（AG-06） | 定时 + 并行（指标计算/归因/效能并行） | 指标查询 · 归因分析 · 报告生成 · 效能数据读取 | A3（仅内部） |

**协作总线（AG-07）**：智能体间通过「任务 + 上下文引用」交接，**事件驱动 + 共享任务表**，任一环失败不影响其他环，全链路可追溯。

**自主度分级 A0~A3 的工程实现**：`agent_autonomy_policy` 策略表（按 智能体 × 动作 配置）+ 工具网关前置校验 + 审批中心。执行流程：拦截 → 查策略 → 边界校验 → 按等级分流（A0 仅建议 / A1 草稿待人审 / A2 执行+可撤回 / A3 全自动）→ 全程审计。

| 铁律 | 工程约束（代码级硬约束，非提示词） |
|---|---|
| 对外内容与触达必须人审（≤A1） | 动作分类表中 `is_outbound=true` 的动作，策略表**禁止配置为 A2/A3**（配置校验时拒绝保存） |
| 价格 / 合同 / 赔偿 / 投诉一律 A0 | 命中敏感动作清单的动作强制 A0，不可覆盖 |
| 默认从严 | 新增智能体/动作默认 A0，需显式上调并留审批记录 |

**边界拦截三层实现**：

| 层 | 手段 | 性质 |
|---|---|---|
| 提示词层 | 系统提示词声明"不做清单" | 软约束，降低无效尝试 |
| **网关层（关键）** | 工具网关注册时**只暴露允许的工具**——不做清单对应的工具根本不注册给该智能体 | **硬约束**，模型无法调用未注册工具 |
| 规则层 | 动作分类 + 风险等级校验（金额阈值、投诉情绪、超知识库问题） | 兜底 |

拦截后：状态置 `NEEDS_HUMAN` + 生成人工待办 + 对象页高亮提示 + 记录拦截原因（供效能分析优化提示词与工具集）。

**人机协同机制**：

| 产品要求 | 工程实现 |
|---|---|
| 可接管 | 任务状态持久化到 `agent_task`（含上下文快照/当前步骤/中间产出）；「接管」→ `TAKEN_OVER` → 中断信号发 Runtime → 前端预填上下文 |
| 上下文无损交接 | 编排状态按**检查点**逐步落库；接管后可从检查点恢复或"继续由智能体推进" |
| 产出即入库 | 智能体经统一 Service 写业务表，自动标记 `source_type=AGENT` / `source_agent_code` / `source_task_id` |
| 来源可追溯 | 业务表审计字段扩展 `source_type`（HUMAN/AGENT/SYSTEM）+ `source_ref`；人工修改 AI 产出保留变更历史 |
| 不阻断 | 智能体与人工并行；冲突用乐观锁（version），冲突提示"该记录刚被智能体更新" |
| 异常升级 | 连续失败 ≥3 次 / 自主度不足 / 命中不做清单 → `NEEDS_HUMAN` + 人工待办 + 通知 |

**任务状态机**：

```
CREATED → QUEUED → RUNNING ─┬→ COMPLETED（产出已入库）
                            ├→ PAUSED → RUNNING
                            ├→ TAKEN_OVER（人工接管）→ COMPLETED / TERMINATED
                            ├→ NEEDS_HUMAN（越界/失败/待审批）→ RUNNING / TERMINATED
                            └→ FAILED（可重试，上限 3 次后 → NEEDS_HUMAN）
```

**效能度量（AC-03）**：任务量/成功率/耗时（`agent_task` 统计）· 采纳率（直接用/改后用/退回/忽略，埋点采集）· 人工介入率 · 节省工时（采纳数 × 标准工时基线）· Token 成本（Advisors 层统一计量）· 越界拦截次数。

**AI 特有风险对策**：

| 风险 | 对策 |
|---|---|
| 提示词注入 | 输入护栏：注入模式检测 + 用户输入与系统指令分隔 + 工具参数白名单校验 |
| 越权访问 | 工具网关注入租户与用户上下文；检索层强制 `tenant_id` + 数据权限（与人工通道同一套） |
| 数据外泄 | 提示词组装前 PII 脱敏；禁送成本价/联系方式等敏感字段；可选私有化模型通道 |
| 幻觉与错误行动 | 结构化输出 Schema 强校验（不合规拒绝执行）+ 写操作前置校验 + A0/A1 审批 |
| 输出内容合规 | 输出护栏：敏感词过滤 + 企业公约约束注入 + 对外内容强制人审 |
| 成本攻击 | 租户级 Token 配额 + 单请求上限 + 异常调用告警 |

### 4.6 L4 前端与角色工作台

**工程结构**：

```
lingxi-web/
├── src/
│   ├── app/                    # 应用骨架（布局、路由、Provider）
│   ├── routes/                 # 路由分区（对齐 11 菜单）
│   ├── features/               # 业务功能模块（按领域组织）
│   ├── components/             # 通用组件
│   ├── packages/lingxi-ui/     # 业务组件库
│   ├── packages/lingxi-request/# 请求层（拦截器/错误/重试/鉴权）
│   ├── packages/lingxi-types/  # 由后端 OpenAPI 自动生成的类型（禁止手写）
│   ├── stores/                 # Zustand（仅 UI 状态）
│   └── locales/                # 语言包（zh-CN / en-US）
└── vite.config.ts
```

**强制约定**：

| 约定 | 结论 |
|---|---|
| 服务端状态 | 一律用 **TanStack Query**；禁止为接口数据做手工缓存与同步 |
| 类型来源 | `lingxi-types` 由后端 OpenAPI 自动生成，**禁止手写接口类型** |
| 权限组件化 | `<LxPermission code="cus:lead:assign">` 包裹，无权限不渲染（而非禁用后报错） |
| 国际化 | 所有文案走 i18n key，**禁止中文字符串写入组件** |
| 懒加载 | 按路由分区代码分割；ECharts 按需引入（地图/热力单独 chunk） |
| 渲染模型 | **纯 SPA，不做 SSR / 不做微前端 / 不做多框架共存** |

**千人千面：配置驱动工作台**（角色工作台的技术核心）——不做五套硬编码页面，做**一套工作台引擎 + 配置**：

- **widget 注册表**：每个卡片声明 `key / title / dataSource / component / defaultSpan / drilldown / compareWindow / permission`
- **布局配置**：按角色下发默认模板（RW-01~05），支持租户级与用户级覆盖
- 卡片能力：可下钻（`drilldown`）· 右上角"三日内变化"（`compareWindow`）· 待办类卡片直接处理（`actions`）· 智能体建议卡置顶槽位（无产出不占位）

**对象详情页统一范式**：客户 / 商品 / 订单 / 服务四类对象共用**通用详情页骨架组件** `ObjectDetailPage`（左信息栏 + 右 Tab：概览 / 明细 / 关联 / 分析），共享骨架 → 学习成本一致、复用率高、AI 生成新详情页有明确模板。

**设计系统落地**：设计令牌以 **CSS 变量 + AntD ConfigProvider theme token 双轨**落地，与高保真原型视觉规范一一对应；`lingxi-ui` 基于 AntD 5 封装业务组件：`LxTable`（全站列表页强制使用）· `LxForm` · `LxChart` · `LxPermission` · `LxDrawer` · `LxAgentSourceTag`（AI 产出标记）· `LxTakeoverButton`（接管）。

> **与原型及 V0 代码的关系**：**原型是交互与视觉契约，不是代码资产**；按组件库重建，不复用原型内联样式。V0 的 Next.js 工程结构、Server Component 划分、Tailwind 内联样式**一律不继承**，可参考的仅是页面信息结构与视觉意图。

### 4.7 安全架构与门禁

**安全设计基线**：

| 维度 | 架构对策 |
|---|---|
| 身份 | OIDC + 短时效 JWT（15min）+ Refresh 轮换 + Token 吊销；密码策略由 Keycloak 强制；MFA 可开 |
| 授权 | 三层权限（功能/行级/字段）+ **数据库 RLS 兜底**；权限决策集中于 `lingxi-platform`，业务模块禁自研判断 |
| 租户隔离 | 拦截器强制注入 + RLS 兜底 + **自动化隔离测试套件**（合并前必跑） |
| 输入 | 参数化查询（MyBatis-Plus 强制）+ 输出编码 + 富文本白名单 + 文件类型/内容校验 |
| 敏感数据 | pgcrypto 加密；日志自动掩码（手机号/邮箱/密钥）；字段权限控制可见性 |
| 凭证 | 渠道 Token 加密托管 + 只在服务端使用 + 前端永不接触 + 轮换机制 |
| 审计 | 全量操作审计（含智能体）+ 按月分区 + 敏感操作二次确认 |
| 依赖供应链 | Dependency-Check + Trivy + **SBOM（CycloneDX）** + BOM 版本锁定 |
| 传输存储 | TLS 1.2+；数据库与对象存储静态加密；备份加密 |
| 接口滥用 | 网关限流（租户级 + 接口级）+ 幂等键 + 签名校验（开放 API） |

**三条不可自动合并红线**：

| 红线 | 触发规则（diff 命中） | 处置 |
|---|---|---|
| 认证与会话 | `lingxi-platform/auth/**` | 强制人工 Review，不得自动合并 |
| 租户隔离与权限 | `*TenantInterceptor*`、`*DataScope*`、`*PermissionEvaluator*`、RLS 策略脚本 | 强制人工 Review |
| 计费 / 配额 / 支付 | `billing/**`、`quota/**`、`payment/**` | 强制人工 Review |

**租户隔离自动化验证套件（6 项，每次合并前必跑）**：

```
① 数据层：以租户 A 的 Token 请求租户 B 的资源 ID → 必须返回 403/404
② 列表层：租户 A 的列表接口 → 结果集必须 100% 属于租户 A（抽样断言）
③ 检索层：租户 A 搜索 → 不得召回租户 B 任何记录（含向量检索）
④ 智能体层：智能体以租户 A 上下文调用工具 → 不得读取租户 B 数据
⑤ 导出/报表：导出行数必须等于本租户计数（对账断言）
⑥ RLS 校验：绕过应用层直连数据库查询 → RLS 必须拦住
```

> 覆盖策略：新增任何带租户数据的接口，**必须同时提交隔离测试用例**（视为契约的一部分，缺失则 CI 失败）。

**安全门禁阈值**：

| 阶段 | 门禁 | 阈值 |
|---|---|---|
| 提交前 | Semgrep + SpotBugs + ESLint + JUnit | 0 高危 |
| PR | Dependency-Check + gitleaks | 0 高危 CVE；0 密钥泄露 |
| 合并前 | Pact 契约 + JaCoCo/Vitest 覆盖率 | 覆盖率 ≥70%（新增代码 ≥80%） |
| 合并后 | Testcontainers 集成测试 + 租户隔离套件 | 全绿 |
| 发布前 | OWASP ZAP DAST | 0 高危 |
| 交付前 | 全量安全审计 + 第三方渗透 | 见商业化门禁清单 |

### 4.8 稳定与可扩展

**高可用与容错**：

| 层面 | 措施 |
|---|---|
| 应用 | 无状态多副本；健康检查就绪/存活分离；优雅停机 |
| 数据库 | 主从流复制 + 自动故障转移；HikariCP 断线重连；读写分离仅用于报表查询 |
| 缓存 | 穿透（空值缓存）/ 击穿（互斥锁）/ 雪崩（过期抖动）三重防护 |
| 外部依赖 | 全部走超时 + 重试（指数退避）+ 熔断；LLM 与外部数据源均有降级路径 |
| 智能体 | 失败自动重试（上限 3 次）→ 转人工；智能体故障不影响业务主流程（降级为纯人工） |
| 数据一致性 | Outbox + 幂等消费；订单、回款额外做对账任务 |
| 备份 | 每日全备 + WAL 归档（时间点恢复）；对象存储版本化；**每季度恢复演练** |

**性能指标（验收口径）**：

| 场景 | 目标 |
|---|---|
| 工作台核心 API | P95 < 300ms（缓存命中 < 100ms） |
| 列表 / 搜索 | P95 < 500ms |
| 详情页（含 360 视图） | P95 < 800ms |
| 智能体交互首包 | 流式输出，首 Token < 2s |
| 内容生成（单条） | < 15s（异步化 + 进度显示） |
| 大数据量导出 | 异步任务 + 下载中心，不阻塞请求 |
| 看板查询 | 走物化视图，P95 < 1s |
| 域间同步调用超时 | 默认 ≤3s（AI / 文件 / 导出除外） |
| 可用性 | 核心链路 99.9% |

**可扩展六条路径**：

| 方向 | 机制 |
|---|---|
| 业务模块扩展 | 模块化单体 + Spring Modulith 边界校验：新增模块 = 新增 Maven 模块 + 注册路由与权限资源 |
| 数据源扩展 | `DataSourceAdapter` 接口：新增数据源只加实现类 |
| 渠道扩展 | `ChannelConnector` 接口：新增触达渠道只加实现类 |
| 智能体能力扩展 | `@Tool` 技能注册 + MCP 白名单：新增能力不改编排主流程；新增智能体 = 配置 + 边界规则 + 工具集 |
| 水平扩展 | 无状态副本扩容；DB/缓存按阈值升级规格 |
| 垂直拆分 | 任一模块可整体剥离为微服务（Interface → RPC，事件不变，业务代码零改动） |

**隧道友好设计（本项目特殊约束）**：组件最小化（隧道降至 2 条）· 连接池快速失败（超时 3s）· 数据任务水位表断点续跑 · 每个夜间任务前先跑 `check-env`（**不通则不派发**）· 全脚本幂等 · 单次夜间只跑 2~4 个任务控制失败半径。

| 3 | **数据底座建设顺序** | **L1 → L2 → L3 → L4** | 先数据底座与企业实体中心，再业务模块；**企业实体中心必须与客户中心同期建设**，否则后期返工 |
