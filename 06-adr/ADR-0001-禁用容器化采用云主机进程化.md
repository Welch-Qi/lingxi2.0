# ADR-0001 禁用容器化，采用云主机进程化部署

| 项 | 内容 |
|---|---|
| 状态 | 已采纳（Accepted） |
| 日期 | 2026-09-11 |
| 决策人 | 产品与架构负责人 |
| 影响范围 | 全部仓库（部署方式、CI、脚本、本地开发） |

## 背景

灵犀系统一期为中小制造企业客户交付，团队规模小、运维人力有限，且已有云主机资源。
需要选择部署与运行时承载方式。

## 决策

**全链路禁用 Docker / K8s**，采用：

- 云主机 + systemd 进程化部署（后端单体、前端 Nginx 静态资源、两个独立进程）
- 数据服务（PostgreSQL 17 / Valkey 9）使用云端托管服务，本地经 **SSH 隧道**接入
- 部署 / 回滚通过脚本（`deploy.sh` / `rollback.sh`，版本目录隔离 + Nginx upstream 切换）
- 配置化 + 脚本化：模型地址、连接串、Key 统一进 `config/*.yml` 与 `.env`

## 理由

1. **故障面更小**：容器编排引入了网络、存储、镜像三层额外故障点；进程化下排障路径为「进程 → 日志 → 端口」三步。
2. **交付对象不匹配**：客户是中小制造企业，现场普遍不具备 K8s 运维能力；容器化平台对他们反而是负担。
3. **最小组件数原则**：每多一个中间件 = 多一条隧道 + 多一个故障点。本地开发仅需 2 条隧道（DB + 缓存）。
4. **回滚更快且可解释**：保留上一版本产物 + 切换 upstream，回滚目标 <5 分钟，且不依赖镜像仓库可用性。
5. **AI Coding 友好**：脚本化的启停与初始化对 AI Agent 是确定性动作（可幂等重跑），镜像构建链路则难以被 AI 稳定验证。

## 被否方案

| 方案 | 否决理由 |
|---|---|
| Docker Compose 本地 + K8s 生产 | 引入两套编排语义；本地与生产环境差异反而更大 |
| K3s 单节点 | 仍需维护容器网络与存储，收益不足以抵消复杂度 |
| 数据服务本地容器化 | 数据落地本地会导致环境漂移与备份责任转移，与「云端托管 + 隧道」冲突 |

## 影响与后续约束

- 【强制】代码库不得出现 `Dockerfile` / `docker-compose` / k8s 清单（附录 D 规则 18，CI 扫描）
- 【强制】应用代码禁止自建 SSH；隧道是基础设施，应用只连 `127.0.0.1:13306` / `127.0.0.1:16379`
- 【强制】隧道需监测与自动重连（autossh + `ServerAliveInterval 30` + `ServerAliveCountMax 3` + `ExitOnForwardFailure yes`）
- 【强制】环境操作只能通过 11 个幂等脚本，禁止手敲命令绕过
- 代价：多实例水平扩展需自行实现（一期为单体，暂不需要）；后续若上多租户大客户专属部署，需重新评估
