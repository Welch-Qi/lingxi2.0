## 规约一：云端 DB/Redis 通过 SSH 隧道连接 —— 监测与自动重连

### 1.1 架构

```
开发机 / CI Runner                    云端
┌─────────────────┐    SSH 隧道     ┌──────────────────┐
│ 本地端口          │ ─────────────→ │ 跳板机/云主机       │
│ 127.0.0.1:13306  │   (autossh)    │  ├ 云 DB  :3306    │
│ 127.0.0.1:16379  │                │  └ 云 Redis:6379   │
└─────────────────┘                └──────────────────┘
应用统一连本地映射端口，永不直连云端真实地址
```

**核心原则**：应用配置里只写 `127.0.0.1:13306` / `127.0.0.1:16379`，云端真实地址、账号只存在于隧道配置中——隧道断了对应用表现为"数据库不可用"，由看护体系负责恢复。

### 1.2 隧道保活三层设计（查证后的生产标准方案）

**第一层：autossh + SSH 心跳（自动重连）**

```bash
# ~/.ssh/config（隧道定义一次，随处使用）
Host lingxi-tunnel
  HostName <云主机IP>
  User tunnel-user
  IdentityFile ~/.ssh/lingxi_tunnel_key
  ServerAliveInterval 30        # 每 30 秒发心跳，防 NAT/防火墙掐断空闲连接
  ServerAliveCountMax 3         # 连续 3 次无响应（~90秒）判定断线
  ExitOnForwardFailure yes      # 端口绑定失败即退出（防止"看似活着实则不通"）
  LocalForward 13306 <DB内网地址>:3306
  LocalForward 16379 <Redis内网地址>:6379

# 启动（-M 0 = 禁用旧式监控端口，用 SSH 心跳，官方推荐）
autossh -M 0 -fN lingxi-tunnel
```

**第二层：服务托管（开机自启 + 崩溃重启）**

- **Linux / CI Runner**：systemd 服务，`Restart=always; RestartSec=10; StartLimitIntervalSec=0`（不限重试频率），`Environment="AUTOSSH_GATETIME=0"`（网络未就绪时持续重试）
- **Windows 开发机**：WSL2 内跑 autossh + systemd；或用"任务计划程序"每 5 分钟执行看护脚本（见下）

**第三层：主动健康检查（WorkBuddy 环境 Agent 职责）**

```bash
# scripts/check-tunnel.sh —— 每次夜间调度前 + 每小时看护必跑
#!/usr/bin/env bash
fail=0
nc -z 127.0.0.1 13306 || fail=1          # TCP 层：端口是否监听
pg_isready -h 127.0.0.1 -p 13306 || fail=1   # DB 层：真探测（本机装 PG 客户端，走隧道连云端库）
redis-cli -p 16379 ping | grep -q PONG || fail=1                   # Redis 层：真 PING
if [ $fail -eq 1 ]; then
  pkill -f "autossh.*lingxi-tunnel"; sleep 3
  autossh -M 0 -fN lingxi-tunnel          # 强制重建隧道
  sleep 10 && nc -z 127.0.0.1 13306 && echo "RECOVERED" \
    || echo "TUNNEL_DOWN_NEED_HUMAN"      # 重建仍失败 → 通知人工，当晚任务暂停派发
fi
```

**流水线集成点**：
1. 22:00 夜间调度第一件事 = `check-tunnel.sh`，隧道不通 → **当晚不派发**，IM 通知人工（避免 Qoder 在断连状态下写出错误配置或假修复）
2. Windows 任务计划 / cron 每 30 分钟自动跑一次看护
3. Qoder 任务简报中写明："连接 DB/Redis 一律用本地映射端口，禁止自行建立 SSH 连接"——**隧道管理权只归环境 Agent**

## 规约二：文档先行（Docs as Authority）

### 2.1 权威文档清单（docs/ 目录，随仓库版本化）

| 文档 | 文件 | 权威范围 |
|---|---|---|
| 产品设计文档 | `docs/01-product-design.md` | 功能边界、模块范围、P0/P1 划分 |
| 数据模型设计 | `docs/02-data-model.md` | 表结构、字段、关系、索引 |
| API 设计文档 | `docs/03-api-design.yaml`（OpenAPI 3.1） | 接口路径、入参出参、错误码 |
| 多租户统一方案 | `docs/04-multi-tenancy.md` | 租户模型、数据隔离策略、租户上下文传递 |
| 安全策略方案 | `docs/05-security-policy.md` | 认证授权、加密、审计日志、敏感数据规则 |
| 契约摘要 | `contracts.md`（从 02/03 派生） | Agent 日常编码的直接依据 |

### 2.2 五条强制规则

1. **文档 = 唯一权威**：代码与文档冲突时，默认代码错误。任何 Agent 发现冲突 → 停止编码 → 创建 `FIX-DOC-*` 任务提交协调 Agent，**由人裁决改文档还是改代码**，裁决结果回写文档后才继续
2. **编码前必读**：AGENTS.md 中规定 Qoder 每个任务开始前必须读取对应模块的文档章节（简报中给出具体章节锚点）
3. **文档变更 = 人工门禁**：Qoder 的任务边界永远不包含 `docs/` 目录；只有人拍板后，由协调 Agent 派 T3 文档任务或人工更新。文档 diff 单独 commit 并打 tag（如 `doc-v1.3`）
4. **验收以文档为准**：qa_gate.sh 的契约校验 = 代码实现的 API schema 对比 `03-api-design.yaml`；数据迁移必须与 `02-data-model.md` 一致；**多租户检查是硬门禁**——任何 SQL/ORM 查询缺少租户条件（对照 04 文档的隔离规则清单）→ 自动 NEEDS_HUMAN
5. **文档先于任务派发**：协调 Agent 派发某模块前检查该模块文档是否齐备，缺文档 → 派"文档补齐"任务给人（T4 提醒），不派开发任务

## 规约三：统一任务清单（TASKS.md）

### 3.1 结构：一张表管全部任务类型

```markdown
# tasks/TASKS.md —— 唯一任务登记处（WorkBuddy 协调 Agent 是唯一写入者）

| ID | 类型 | 模块 | 标题 | tier | 依赖 | 状态 | 简报/产物 |
|----|------|------|------|------|------|------|-----------|
| M1-DEV-001 | DEV | M1 | 认证服务实现 | T1 | — | MERGED | tasks/M1-backend.md |
| M1-TEST-001 | TEST | M1 | 认证契约测试 | T3 | M1-DEV-001 | QA_PASS | tasks/M1-test.md |
| M2-DEV-001 | DEV | M2 | 权限矩阵 API | T1 | M1-DEV-001 | READY | tasks/M2-perm.md |
| FIX-M2-001 | FIX | M2 | 租户过滤缺失 | T2 | QA报告 | READY | tasks/FIX-M2-001.md |
```

- **类型**：`DEV`（开发）/ `TEST`（测试用例与环境）/ `FIX`（Bug 修复）/ `DOC`（文档补齐，人工）
- **状态机**：`BACKLOG → READY → IN_PROGRESS → TESTING → QA_PASS → MERGED`，分支 `QA_FAIL`（自动生成 FIX 任务后归档）、`NEEDS_HUMAN`（冻结）、`INTERRUPTED`（夜间硬截止断点）

### 3.2 单一写入者原则

- **WorkBuddy 协调 Agent = 唯一写入者**；Qoder 只读 TASKS.md，只写自己的 `result.json`——避免双写冲突
- Qoder 的简报由派发时从 TASKS.md 对应行 + 文档章节自动组装

### 3.3 Bug → 修复任务自动转化闭环

```
验收 QA_FAIL
  → 验收 Agent 生成 bug 报告（reports/bugs/FIX-M2-001.md：复现步骤+失败测试+SAST证据）
  → 在 TASKS.md 新增 FIX-M2-001（tier 按严重度：数据错误/安全=T1~T2，UI/样式=T2~T3）
  → 状态 READY，进入当晚或次晚派发队列
  → 修复完成重新验收 → 通过则 FIX 任务 MERGED 并回链原 DEV 任务
  → 同一问题 fix 轮次 ≥5 → 升级 NEEDS_HUMAN，人工接手
```

### 3.4 派发规则（协调 Agent 每晚执行）

按依赖排序取 `READY` 任务（≤4 个/晚）→ 优先级：`FIX > DEV > TEST > DOC` → 并行任务必须模块隔离（不同模块才可同晚并行）→ 派发后置 `IN_PROGRESS`。

## 规约四：配置化与脚本化

### 4.1 配置统一管理

```
config/
├── app.yml            # 应用配置：端口、日志级别、环境标识
├── db.yml             # DB：host=127.0.0.1, port=13306（永远本地映射端口）
├── redis.yml          # Redis：host=127.0.0.1, port=16379
├── model.yml          # 模型路由表：tier→model ID 映射、API 地址（Qoder 侧）
└── tunnel.yml         # 隧道参数：端口映射、心跳间隔（供 check-tunnel.sh 读取）
.env                   # 秘密：DB密码、API Key、SSH Key 路径（gitignore，绝不入库）
.env.example           # 秘密的字段模板（入库，新人照抄填值）
```

**代码中禁止出现**：数据库连接串、密码、API Key、云端 IP、模型名称。全部通过配置模块注入（如 `config.get('db.url')`）。

**AGENTS.md 强制条款 + 自动检查**：qa_gate.sh 对每次 diff 执行反模式扫描：

```bash
grep -rEn "(password|api[_-]?key|secret)\s*[:=]\s*['\"][^'\"]{8,}" src/ && fail
grep -rEn "(jdbc|postgres(ql)?|redis|mysql(5[67])?)://[^$@{]" src/ && fail   # 连接串硬编码
grep -rEn "qwen[0-9.-]*(max|plus)" src/ && fail                              # 模型名硬编码
```

命中任意一条 → 验收直接 FAIL，生成 FIX 任务。

### 4.2 脚本清单（所有环境操作只走脚本，Agent 禁止手敲环境命令）

| 脚本 | 职责 | 使用者 |
|---|---|---|
| `scripts/tunnel-up.sh` / `check-tunnel.sh` | 建隧道 / 健康检查+自动重建 | 环境 Agent + 看护定时任务 |
| `scripts/init-db.sh` | 建库、跑迁移、灌种子数据（幂等，可重复执行） | 环境 Agent |
| `scripts/start-dev.sh` / `stop-dev.sh` | 起/停前后端服务（读取 config/） | 环境 Agent |
| `scripts/check-env.sh` | 一键体检：隧道→DB→Redis→服务健康，输出 JSON | 夜间调度第一步 + 晨间报告 |
| `scripts/qa_gate.sh` | 验收门禁：测试+SAST+契约 diff+硬编码扫描 | 验收 Agent |
| `scripts/qoder_client.sh` | 派发（tier 路由）/轮询/取结果 | 协调 Agent |

**幂等要求**：所有脚本必须可重复执行不出错（init-db 用 migration 工具管理版本；start 前先 stop 残留进程）——这是"断点续跑"能在环境层成立的前提。

## 五、四条规约如何嵌入现有流水线

| 流水线环节 | 嵌入的规约动作 |
|---|---|
| 22:00 夜间调度 | 先 `check-env.sh`（规约一）→ 读 TASKS.md 取 READY 任务（规约三）→ 按简报+文档章节派发（规约二）→ 全程用脚本与配置（规约四） |
| Qoder 执行 | 读 AGENTS.md 强制条款：连本地映射端口、禁碰 docs/、禁硬编码秘密、只读 TASKS.md |
| WorkBuddy 验收 | qa_gate.sh 增加硬编码扫描 + 多租户隔离检查；文档一致性作为契约校验的基准 |
| Bug 闭环 | QA_FAIL 自动生成 FIX 任务入清单，tier 按严重度路由 |
| 08:00 晨间报告 | 汇总任务清单状态变化 + 隧道/环境健康记录 + NEEDS_HUMAN 清单 |
